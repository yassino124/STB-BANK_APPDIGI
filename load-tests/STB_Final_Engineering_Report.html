Test de Sécurité — Race Condition (Double-Spend) ✅ CORRIGÉE

Détection proactive d'une vulnérabilité sur les transactions financières simultanées

🎯 Scénario du Test
Compte A (expéditeur) : solde X DT Requête A ──┐ POST /transactions/transfer │ { fromId: A, toId: B, amount: 800 } ├──► Lancées à la même milliseconde ←──┤ Requête B ──┘ POST /transactions/transfer │ { fromId: A, toId: B, amount: 800 }──┘ Attendu : 1 RÉUSSI + 1 REFUS (solde insuf.) Obtenu : 2 RÉUSSIS ⚠️ Double-Spend détecté
📋 Résultat Console — Node.js (réel)
🚀 Test Race Condition démarré... ⚡ Lancement 2 virements simultanés 800 DT Solde du compte expéditeur : exactement 800 DT ✅ Requête 1 — ACCEPTÉE (HTTP 201) ref: TRF-MST36CUD-WEX87H montant: 800 DT — status: COMPLETED 🛡️ Requête 2 — BLOQUÉE (HTTP 400) message: Insufficient balance or account unavailable (concurrent request blocked) ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ 🛡️ PROTÉGÉ — 1 virement accepté, 1 bloqué ! → findOneAndUpdate($gte) fonctionne ✅ → Le compte ne peut PAS tomber en négatif. ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🔍 Analyse Technique & Solution Appliquée
⚠️
Avant (Vulnérable) : Les requêtes lisaient le solde avant de décrémenter via findByIdAndUpdate. Les deux requêtes validaient la condition solde > totalDebit simultanément.
// ❌ Code initial (vulnérable) if (account.solde < totalDebit) { throw BadRequestException(...); } // ↑ Les 2 req passent ici avant màj await Model.findByIdAndUpdate(id, { $inc: { solde: -totalDebit } });
// ✅ Code corrigé (Atomique) const acc = await Model.findOneAndUpdate( { _id: id, solde: { $gte: totalDebit } // ← Filtre }, { $inc: { solde: -totalDebit } }, { new: true } ); if (!acc) throw BadRequestException();
🛡️
Vulnérabilité CORRIGÉE — findOneAndUpdate() atomique avec vérification dans le filtre La correction consiste à inclure la vérification du solde directement dans le filtre de findOneAndUpdate({ solde: { $gte: totalDebit } }). MongoDB garantit l'atomicité de cette opération : si deux requêtes arrivent simultanément, une seule trouvera le document avec un solde suffisant. L'autre reçoit null → HTTP 400. Fonctionne sans Replica Set. Le controller a également été corrigé pour relancer l'exception (throw error) au lieu de retourner HTTP 201 avec un body d'erreur.
